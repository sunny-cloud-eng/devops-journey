# INC-003: High Memory Usage Investigation

## Incident Summary

A controlled high-memory scenario was performed to practise Linux memory troubleshooting.

A Python process was created to allocate approximately 512 MiB of memory. The process was identified, terminated gracefully, and memory recovery was verified.

## Environment

- Platform: GitHub Codespaces
- Operating System: Linux
- Total memory: Approximately 7.8 GiB
- Swap: Not configured
- Incident type: High memory usage
- Severity: Training simulation
- Service impact: None

## Objective

The objective of this exercise was to learn how to:

- Check overall Linux memory utilization.
- Understand free and available memory.
- Identify memory-consuming processes.
- Interpret RSS and process state.
- Terminate a controlled process gracefully.
- Confirm that memory was released.
- Document the investigation.

## Initial Memory Baseline

Command used:

    free -h

Initial output:

                   total        used        free      shared  buff/cache   available
    Mem:           7.8Gi       2.0Gi       267Mi        62Mi       5.9Gi       5.8Gi
    Swap:             0B          0B          0B

### Initial Observations

- Total memory: 7.8 GiB
- Used memory: 2.0 GiB
- Free memory: 267 MiB
- Buffer/cache: 5.9 GiB
- Available memory: 5.8 GiB
- Swap usage: 0 B

Although free memory was only 267 MiB, approximately 5.8 GiB was available to applications.

The system was therefore not experiencing memory pressure. Linux was using a significant amount of otherwise-unused RAM for buffers and cache.

## Initial System Investigation

Command used:

    top

Relevant observations:

    Tasks: 20 total, 2 running, 18 sleeping, 0 stopped, 0 zombie
    CPU idle: 84.2%
    I/O wait: 0.0%

### Interpretation

- The server had 20 processes.
- Two processes were running.
- Eighteen processes were sleeping.
- No stopped processes were present.
- No zombie processes were present.
- CPU idle time was 84.2%.
- I/O wait was 0%.
- No CPU or I/O pressure was observed.

## Initial Process Investigation

Command used:

    ps aux --sort=-%mem | head

The highest initial memory-consuming process was a Visual Studio Code Node extension-host process.

Observed information:

- PID: 1520
- Process: Node extension host
- Memory usage: 3.8%
- RSS: 313944 KiB
- Approximate physical-memory usage: 307 MiB

The process was part of the GitHub Codespaces and Visual Studio Code environment.

No corrective action was required because approximately 5.8 GiB of memory remained available.

The process was not terminated because it supported the active development environment.

## Controlled Memory Test

A temporary Python process was started to allocate approximately 512 MiB of memory.

Command used:

    python3 -c 'import time; x=bytearray(512*1024*1024); print("Allocated 512 MiB"); time.sleep(300)' &

### Command Explanation

- python3 -c runs Python code directly from the command line.
- bytearray(512*1024*1024) allocates approximately 512 MiB of memory.
- print confirms that the memory allocation was completed.
- time.sleep(300) keeps the process alive for 300 seconds.
- The ampersand runs the process in the background.

## Memory Condition During the Test

Command used:

    free -h

Output during the test:

                   total        used        free      shared  buff/cache   available
    Mem:           7.8Gi       2.4Gi       181Mi        64Mi       5.6Gi       5.4Gi
    Swap:             0B          0B          0B

### Observations During the Test

- Used memory increased from 2.0 GiB to 2.4 GiB.
- Available memory decreased from 5.8 GiB to 5.4 GiB.
- Swap usage remained 0 B.
- The system continued to have sufficient available memory.
- No service impact was observed.

## Identifying the Memory-Consuming Process

Command used:

    ps -eo pid,ppid,stat,%cpu,%mem,rss,cmd --sort=-rss | head

The controlled Python process appeared at the top of the list.

Process details:

- PID: 7809
- PPID: 3326
- Process state: S
- CPU usage: 1.4%
- Memory usage: 6.5%
- RSS: 534444 KiB
- Command: python3

### RSS Calculation

    534444 KiB / 1024 = approximately 522 MiB

The process was holding approximately 522 MiB of physical memory.

This was close to the requested 512 MiB allocation. The additional memory was associated with the Python process itself.

## Process-State Interpretation

The process state was:

    S

S means that the process was sleeping.

The process was sleeping because it was executing:

    time.sleep(300)

Sleeping did not mean that the process had stopped. The process continued to exist and hold its allocated memory while waiting for the sleep period to finish.

## Root Cause

The increase in memory utilization was caused by the controlled Python process.

The process intentionally allocated approximately 512 MiB using a Python byte array and held the memory while sleeping.

This was a training simulation and not an application defect or production incident.

## Corrective Action

The test process was terminated gracefully using:

    kill 7809

The normal kill command sends the SIGTERM signal by default.

SIGTERM requests that the process terminate gracefully.

A forceful termination using the following command was not required:

    kill -9 7809

SIGKILL should generally be considered only when a process does not respond to a normal termination request and the action has been approved.

## Process-Termination Verification

Command used:

    ps -p 7809

Output:

    PID TTY          TIME CMD

Only the column heading was displayed. No process information appeared below the heading.

This confirmed that PID 7809 no longer existed.

The terminal also displayed a message confirming that the Python process had been terminated.

## Memory-Recovery Verification

Command used:

    free -h

Output after terminating the process:

                   total        used        free      shared  buff/cache   available
    Mem:           7.8Gi       1.9Gi       663Mi        64Mi       5.6Gi       5.9Gi
    Swap:             0B          0B          0B

### Final Observations

- Used memory decreased from 2.4 GiB to 1.9 GiB.
- Free memory increased from 181 MiB to 663 MiB.
- Available memory increased from 5.4 GiB to 5.9 GiB.
- Swap usage remained 0 B.
- The controlled Python process was no longer running.
- The memory allocated by the Python process was successfully released.

## Resolution

The controlled memory-consuming process was identified using process-level memory information.

The process was terminated gracefully using SIGTERM. Its termination was verified using ps, and memory recovery was confirmed using free -h.

The server returned to its healthy baseline condition.

## Troubleshooting Flow

1. Receive or observe the high-memory alert.
2. Check overall memory using free -h.
3. Focus on available memory, not only free memory.
4. Inspect system activity using top.
5. Sort processes by memory consumption using ps.
6. Identify the PID and complete command.
7. Assess the application and business impact.
8. Confirm ownership and obtain approval if required.
9. Take the approved corrective action.
10. Verify that the process has stopped.
11. Confirm memory recovery.
12. Document the incident.

## Commands Practised

Check overall memory:

    free -h

Inspect system activity:

    top

List processes by memory percentage:

    ps aux --sort=-%mem | head

List processes by RSS:

    ps -eo pid,ppid,stat,%cpu,%mem,rss,cmd --sort=-rss | head

Create the controlled memory process:

    python3 -c 'import time; x=bytearray(512*1024*1024); print("Allocated 512 MiB"); time.sleep(300)' &

Inspect a specific process:

    ps -p 7809 -o pid,ppid,stat,%mem,rss,cmd

Terminate the process gracefully:

    kill 7809

Verify process termination:

    ps -p 7809

## Important Concepts

### Free Memory

Free memory is RAM that is currently unused.

A low free-memory value alone does not prove that the server is experiencing a memory problem.

### Available Memory

Available memory is the estimated amount of memory that can be provided to applications without creating serious memory pressure.

During this investigation, available memory was more useful than the free-memory value.

### Buffers and Cache

Linux uses otherwise-unused RAM for buffers and cache to improve system performance.

This memory can be reclaimed when applications require additional memory.

### RSS

RSS means Resident Set Size.

RSS represents the approximate amount of a process's memory currently held in physical RAM.

### Swap

Swap is disk space that can support physical memory when required.

This GitHub Codespaces environment had no swap configured:

    Swap: 0 B total

Zero swap usage was therefore expected. It was not, by itself, proof that the server was healthy.

### SIGTERM

SIGTERM asks a process to terminate gracefully.

It is normally preferred before forceful termination.

### SIGKILL

SIGKILL immediately stops a process and does not allow normal process cleanup.

It should not be the first action during routine troubleshooting.

## Production Safety Considerations

Before terminating a process in a production environment:

1. Confirm the correct PID.
2. Review the complete process command.
3. Identify the application or service associated with the process.
4. Check whether the process is business-critical.
5. Review the current application impact.
6. Capture troubleshooting evidence.
7. Follow the approved standard operating procedure.
8. Obtain approval when required.
9. Prefer a graceful service stop or SIGTERM.
10. Verify service recovery after taking corrective action.
11. Escalate when process ownership is unclear.
12. Never terminate an unfamiliar process only because it is using the most memory.

## Preventive and Monitoring Recommendations

- Monitor available memory instead of relying only on free memory.
- Monitor memory usage trends instead of relying on one snapshot.
- Identify high-memory processes using top and ps.
- Record the PID, RSS, command, and observed impact.
- Investigate processes whose memory usage continues to grow.
- Configure appropriate monitoring thresholds.
- Follow an approved restart or escalation procedure.
- Verify memory recovery after remediation.
- Document findings and actions in the incident ticket.

## Key Learning

Low free memory alone does not indicate a memory problem.

The following items should be evaluated together:

- Available memory
- Buffers and cache
- Process-level memory consumption
- Swap configuration and usage
- Application impact
- System behavior
- Memory recovery after corrective action

A support engineer should not terminate a process only because it consumes the most memory.

The process identity, business function, impact, ownership, and approved procedure must be checked first.

## Interview Explanation

When investigating a high-memory alert, I first check the server using free -h.

I focus mainly on available memory instead of judging the condition only from free memory because Linux uses otherwise-unused RAM for buffers and cache.

I then use top or ps sorted by memory consumption to identify the process using the most physical memory.

I verify the PID, complete command, RSS, process ownership, and application impact before taking corrective action.

In this exercise, I identified a Python process consuming approximately 522 MiB of resident memory. I terminated it gracefully using SIGTERM, verified that the PID no longer existed, and confirmed that available memory increased from approximately 5.4 GiB to 5.9 GiB.

This confirmed that the Python process was responsible for the additional memory consumption and that the allocated memory was successfully released.
