# INC-002: High CPU Utilization
 
## Incident Details
 
- **Severity:** P2 - High
- **Server:** cloudcare-web-01
- **Alert:** CPU utilization above 85%
- **Reported impact:** Application response time increased
- **Assignment group:** Cloud Operations
- **Environment:** Ubuntu-based GitHub Codespaces container
 
## Initial Baseline
 
Before reproducing the incident:
 
- CPU user time: 5.9%
- CPU system time: 5.2%
- CPU idle: 88.9%
- CPU I/O wait: 0.0%
- Available memory: Approximately 5.9 GiB
- No process showed unusually high CPU utilization
 
**Assessment:** The environment was initially healthy.
 
## Test Workload
 
A controlled CPU-intensive process was started using:
 
```bash
timeout 900 yes > /dev/null &

The timeout command acted as the supervisor, while the yes command generated the CPU workload.

Investigation Commands
Shell
uptime
top
pgrep -a -P 7223
ps -o pid,ppid,user,stat,pri,ni,%cpu,%mem,etime,cmd -p 7226
ps -o pid,ppid,user,stat,%cpu,etime,cmd -p 7223,7226
cat /proc/7226/status | head -n 12
readlink -f /proc/7226/exe
kill -15 7226
ps -p 7226 -o pid,ppid,stat,%cpu,cmd
ps -p 7223,7226 -o pid,ppid,stat,%cpu,cmd
Investigation Findings
CPU Condition

During the incident:

CPU user time increased to 30.8%.
CPU system time increased to 34.3%.
CPU idle decreased from 88.9% to 35.0%.
CPU I/O wait remained at 0.0%.

Assessment: CPU utilization increased significantly, but the issue was not related to disk I/O wait.

Initial PID Investigation

The initially captured PID was:

Plain Text
PID 7223: timeout 900 yes

This process showed:

State: Sleeping
CPU usage: 0.0%

The process was a supervisor and not the actual CPU consumer.

Parent-Child Investigation

The following command located the child process:

Shell
pgrep -a -P 7223

Result:

Plain Text
7226 yes

Confirmed process hierarchy:

Plain Text
timeout (PID 7223)
└── yes (PID 7226)
High-CPU Process

The child process showed:

PID: 7226
Parent PID: 7223
Owner: codespace user
State: Running
Priority: 19
Nice value: 0
CPU utilization: Approximately 98.4%
Memory utilization: 0.0%
Executable: /usr/bin/yes

Assessment: The yes process was continuously generating output and consuming almost one complete CPU core.

/proc Verification

The file /proc/7226/status confirmed:

Process name: yes
State: Running
PID: 7226
Parent PID: 7223
User ID: 1000
No debugger was attached

The executable link confirmed:

Plain Text
/usr/bin/yes
Corrective Action

The process was asked to terminate gracefully using:

Shell
kill -15 7226

Signal 15 is SIGTERM.

SIGKILL was not required because the process responded successfully to SIGTERM.

Recovery Verification

After sending SIGTERM:

PID 7226 no longer existed.
PID 7223 also exited.
CPU idle recovered from 35.0% to 92.6%.
CPU I/O wait remained at 0.0%.
No zombie processes were present.
The highest visible process consumed approximately 1.0% CPU.
Root Cause

The /usr/bin/yes process continuously generated output and consumed approximately 98% of one CPU core.

The workload was intentionally started for this controlled troubleshooting exercise.

Resolution

The high-CPU child process was terminated gracefully using SIGTERM.

CPU utilization returned to its normal baseline without:

Rebooting the server
Restarting unrelated services
Using SIGKILL
Preventive Actions

In a real production incident:

Determine who or what launched the process.
Check the parent process, service, cron job, script, or deployment.
Review relevant application and system logs.
Confirm whether the process could restart automatically.
Configure CPU alerts with sufficient duration to reduce false positives.
Verify application response time after resource recovery.
Document the complete process tree before terminating a process.
Key Learning

The first PID discovered may belong to a supervisor rather than the actual CPU consumer.

A support engineer should verify:

Process ID
Parent process ID
Process owner
Process state
CPU and memory utilization
Complete command
Executable path
Parent-child relationship

Use SIGTERM first whenever possible. Use SIGKILL only when graceful termination fails and the business impact justifies immediate termination.

Stopping the process restores CPU capacity, but it does not by itself explain why the process started.
